# Grok R3 (terracing): appraisal

Delivered 2026-09-26. Appraised by Claude against the code; Grok's text isn't kept.

**Grade: fair.**
- The recommendation (mark edited cells so the existing smoothing can skip them) is right: it's the idea D62 already named.
- But two of its four options rest on a misunderstanding of where terraces come from, and it gets how far the smoothing reads wrong.

## Claims checked against the code

| Grok said | True? | What the code says |
|---|---|---|
| Terraces come from the mesher's corner placement | Half | The deeper cause is that the ground is **whole cells**. Any slope gentler than one cell up per cell across becomes one-cell steps, whatever made the heights. `HillsHeight` returns an **integer** (terrain.h), not a continuous surface. |
| Option 2: blend corners toward "the continuous height function" | Doesn't hold | What the game can call is whole-cell heights. Going to the noise underneath would need a new function. Worse, pulling the surface away from its cells makes the drawn ground disagree with the solid cells: digging, picking and building work on cells. |
| Option 3: a new terrain version removes terraces | False | A new height function still has to be rounded to whole cells, so gentle slopes still step. A new version can only change *where* slopes are gentle, not the steps. |
| Option 4: bevel steps "smaller than half a block" | Misread | Neighbouring cells differ by 0 or by whole blocks; there's no half-block step to test for. What's left of the idea (ease one-cell steps between natural cells) is what the existing smoothing pass already does (`FacetShape::terrace`, facetmesh.cpp). |
| A corner is smoothed when "none of its four cells" is edited | Too narrow | A corner touches 8 cells, and the smoothing pass reads more than one cell around a corner. The edited test has to cover the same neighbourhood the pass reads, or an edit next door still gets softened. |
| The edited flag goes in the cell's spare state byte | True, with a cost | Each cell has a state byte (world.h, `Chunk::state`) and saves already store it. But the mesher's copy of a chunk (`GroundCells`) carries only the materials, so the state (or one bit of it) must be copied too: 20³ more bytes per chunk copy on the main thread. |
| Old saves: scan and mark cells that differ from the generator | True, and simpler than it said | A save holds only chunks that differ from the generator (worldfile.h), so the scan need only touch those, comparing each cell with a freshly generated column (about 0.05 ms a column). |
| Seams and collision come for free | True | Chunks share their corner rules and collision uses the drawn corners (D39). An edited flag copied with the 2-cell margin keeps both true. |

## Verdicts

| Option | Verdict |
|---|---|
| 1. Mark edited cells; turn the existing smoothing back on, skipping them | **Keep**: the plan. It's also what the edit tests need (they're why terracing was switched off, D62). |
| 2. Smooth toward the height function | **Drop**: breaks the tie between drawn ground and cells. |
| 3. New terrain version against terraces | **Drop** as a terrace fix. A terrain v3 may still come for other reasons (caves, R6). |
| 4. Micro-bevel | **Drop**: it's the existing smoothing pass under another name. |

**What we'd build, when W055 is picked up:** an "edited" bit set by every player edit, copied into the mesher's cells with the margin; the smoothing pass skips any corner whose neighbourhood contains an edited cell; and a one-time scan of saved modified chunks for old worlds.
